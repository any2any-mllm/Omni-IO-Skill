# Dependency Inference Rules

This file defines two types of dependency rules:

1. **Principles for declaring dependencies during planning:** which tasks need `depends_on`
2. **Automatic injection rules during execution:** how upstream outputs are passed downstream

---

## 1. Dependency Declaration Principles

### Core Principle: Declare Conservatively

When a dependency is **uncertain**, Claude should declare it rather than omit it:

- **Missing dependency:** A downstream task starts in parallel before its upstream task is complete and reads an empty or stale asset, producing an incorrect result at high cost.
- **Unnecessary dependency:** A downstream task waits for an upstream task it does not need, which only reduces parallel efficiency at low cost.

Therefore, err on the side of declaring `depends_on`.

---

### Cases That Require a Dependency

The downstream task must declare an upstream dependency in the following situations.

#### 1. Content Reference

The downstream prompt directly references content generated upstream, such as "use the image above as the first frame" or "follow the character design above."

```json
// Use the image as the video's first frame
{"id": "vid1", "type": "video", "prompt": "..., use the image generated by img1 as the first frame", "depends_on": "img1"}
```

#### 2. Format or Media Dependency

The downstream task requires a specific upstream file or URL as an input parameter, such as an image URL for image-to-3D.

```json
// Use the image as the 3D model's visual reference
{"id": "3d1", "type": "3d", "prompt": "...", "depends_on": "img1"}
```

#### 3. Strong Semantic Consistency

The downstream content must match the upstream output closely, and a prompt written before the upstream result exists might differ from the actual output.

---

### Cases That Do Not Require a Dependency

Tasks can run independently and in parallel without `depends_on` when:

- They do not reference one another's content and each prompt fully describes its required scene.
- Their types are orthogonal, such as image generation and background-music generation.

```json
// The wallpaper and music are independent
{"id": "img1", "type": "image", "prompt": "A forest at dawn..."},
{"id": "mus1", "type": "music", "prompt": "A forest at dawn... meditative style"}
```

## 2. Automatic Upstream-Result Injection

After an upstream task completes, Claude injects its output into the downstream tool-call parameters according to the dependency type. Do not pass URLs or `asset_id` values manually in the prompt.

### Injection Table

| Dependency | Injected Upstream Output | Method |
|------------|--------------------------|--------|
| `image → video` | Upstream image URL | Video-generation first-frame parameter, `first_frame_url` |
| `image → 3d` | Upstream image URL | 3D-generation reference-image parameter, `reference_image_url` |

### When Injection Occurs

- Injection and downstream execution occur only after the upstream task completes.
- Claude performs injection while scheduling; it is transparent at the prompt level.

### Injection Example

```
Task vid1 depends_on img1:

img1 completes and Claude receives:
  img1.url = "/Users/alice/OmniIO/img_a3f2c1.png"   ← local file path

When Claude starts vid1, it automatically adds this MCP tool-call parameter:
  first_frame_url = "/Users/alice/OmniIO/img_a3f2c1.png"

Both the Wan and Kling providers accept a local path as the first frame; internally,
it is converted to a base64 data URI before being passed to the API.
vid1.prompt only needs to state the semantic intent and does not need path-transfer details.
```

## 3. Multiple Dependencies (`type: "code"` / `"markdown"` Only)

When `depends_on` is an array such as `["img1", "3d1", "vid1"]`, it is valid only for tasks with `type: "code"` or `type: "markdown"`. As explained in `formats/declare_format.md`, other task types are single MCP calls with fixed parameter signatures and cannot accept an arbitrary number of upstream assets. Claude writes `code` and `markdown` files natively, so it can call `get_asset()` separately for each `asset_id` and genuinely consume multiple dependencies.

**Trigger condition:** AND logic; execution starts only after every listed upstream task completes:

```
Trigger condition: img1.status == "completed" AND 3d1.status == "completed" AND vid1.status == "completed"
```

**Injection method:** There is no automatic parameter injection because there is no fixed parameter name comparable to `first_frame_url` or `reference_image_url`. Before writing the file, Claude calls `get_asset()` for every upstream `asset_id`, obtains each local path, and decides how to reference the files in the output.

**If any upstream task fails:** Mark the downstream `code` or `markdown` task `cancelled`, do not write its file, and record the reason in the `failed` field of `output_format`, following the same logic used for a failed single dependency in the next section.

Declaring multiple dependencies for any other task type is a planning error. Split the work into a single-dependency chain or make the tasks independent and parallel.

**The array is a scheduling instruction and must not be passed to any tool.** When calling `register_asset()` after writing the file, **do not** pass the `depends_on` array unchanged. The `depends_on` parameter of `register_asset()` accepts one string and has a different meaning: it records lineage from a single earlier version, not the assets that had to finish before this task. In a multi-dependency case, normally omit `depends_on` when calling `register_asset()`. See `skills/generate/code.md` and `skills/generate/markdown.md`.

---

## 4. Handling Upstream Failure

When an upstream task has `failed`:

- Mark each downstream task `cancelled`.
- Do not inject results or start its API call. For `code` or `markdown`, do not write the file.
- Record the reason in the `failed` field of `output_format`.

## 5. Dependency Graph Examples

### Example 1: Linear Chain

```
img1 → 3d1
```

Order: complete img1 → start 3d1

### Example 2: Fan-Out

```
img1 → vid1
img1 → 3d1
mus1 (independent)
```

Wave 0: img1, mus1 in parallel  
Wave 1: vid1, 3d1 start in parallel after img1 completes

### Example 3: Mixed Graph

```
img1 → vid1
img1 → 3d1
mus1 (independent)
sfx1 (independent)
```

Wave 0: img1, mus1, sfx1 in parallel  
Wave 1: vid1, 3d1 start in parallel after img1 completes

### Example 4: Multiple Dependencies Converging on `code`

```
img1 → 3d1 → code1
img1 → vid1 → code1
code1 depends_on: ["img1", "3d1", "vid1"]
```

Wave 0: img1  
Wave 1: 3d1 and vid1 start in parallel after img1 completes; they do not depend on each other  
Wave 2: code1, with `type: "code"`, starts after img1, 3d1, and vid1 all complete. Claude calls `get_asset()` for each path and writes them into the webpage.

The multi-dependency behavior of `markdown` is identical, except the final output is a `.md` file rather than `.html`.
